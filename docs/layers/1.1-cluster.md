# Layer 1.1 — Cluster autodiscovery

**Status:** Fabric Bootstrap (milestone 1)  
**Depends on:** 1.0 adaptive stack (discover, fabric, Resource Graph, scheduler, work execution)

## What landed

- Resident node: `omls daemon` (same binary as `omlsd`).
- Persistent `node_id` in the daemon data directory. An existing file wins over a later machine-id change.
- LAN advertisement and browse of `_omls._tcp.local` (node id, protocol, address, OS, virt).
- Membership: ready, unavailable, and automatic rejoin with the same id. Boot order does not matter.
- Coordinator is the ready member with the lowest `node_id`. Loss of that node elects the next one. It is not a permanent Master machine.
- Local socket API. `omls status`, `omls nodes`, `omls cluster`, and `omls graph` do not take a master address.
- `omls run-demo` forwards to the current coordinator, which still uses the 0.3/0.6 scheduler and agent work execution.
- `omls master` and `omls agent` remain for debug and compatibility.
- `omls.service` starts the daemon at boot after it has been installed. The unit is not required to run the daemon by hand.

## Out of scope

`omls run` for arbitrary programs such as FFmpeg, and enterprise orchestration. A fixed RAM reservation for a memory or graphics slice is layer 1.3.
