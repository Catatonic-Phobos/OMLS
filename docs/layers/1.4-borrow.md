# Layer 1.4 — Peer borrow

**Status:** experimental reservation bookkeeping; application work is not offloaded
**Depends on:** 1.3 cache listener, 1.1 LAN membership

## What landed

- Each daemon publishes CPU, free RAM, and free VRAM on `GET /v1/offer` (`:7444`).
- A machine at or above 80% CPU or RAM requests a named 32 MiB cache reservation on a peer with free RAM.
- A machine at or above 80% GPU memory requests a named 32 MiB cache reservation marked as graphics on a peer with free VRAM.
- The same offers produce the same assignment on every node. The elected coordinator is not asked.
- The slice stays until the machine drops under 70%, or a different peer becomes the one with room.
- Each slice is 32 MiB, named by requester and function, so a texture and a shader on one peer do not overwrite the 1.3 reservation.
- `omls borrow` prints the assignment and places a small synthetic proof payload. The daemon repeats the check every 5 seconds.
- `omls status` shows `borrow: texture … shader …`.

## Out of scope

These reservations do not transfer an application's textures, shaders, or live frames, and do not allocate another machine's VRAM for a process. No automatic application workload offload is implemented by this layer.
